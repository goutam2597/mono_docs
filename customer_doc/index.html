01 / IDENTITY

The customer app at a glance

mono_customer is a conventional Provider-based Flutter application for the Mono marketplace. Its Dart description is “Mono marketplace customer app.” The display name is Mono and the declared version is 1.0.0+1. This guide documents the app exactly as it is implemented.

06 / NETWORKING

Dio, the default base URL, and unprefixed endpoints

The active compiled default is the placeholder https://your-domain.com/api/v1 — a development default you must point at your own API root before building, not a production URL. ApiClient applies a 15-second connect timeout, 60-second receive timeout, JSON headers, Bearer token, X-Locale, Accept-Language, and relative media URL resolution.

Point the app at your server — step by step

The compiled URL inside the app is a placeholder. Connect the app to your own backend once, before any real testing — five minutes, one file, no other code changes:

  1. Open the API client file.

    In your Flutter project, open lib/services/api_client.dart in any code editor (VS Code or Android Studio).

  2. Find the default URL.

    Search the file for defaultBaseUrl. You will see one line like static const defaultBaseUrl = '...'; — this single value decides which server the whole app talks to.

  3. Replace it with your domain.

    Change the value to your own API root, keeping the /api/v1 suffix exactly as your server exposes it: static const defaultBaseUrl = 'https://your-domain.com/api/v1';. Save the file.

  4. Run and log in.

    Start the app again with flutter run -d <device>, then log in with an account that exists on your server. The storefront should now load your products and categories.

  5. Check images too.

    Product and banner images resolve against the same base URL, so if JSON loads but pictures do not, run php artisan storage:link on the server and confirm /storage is reachable in the browser.

Release rule: published builds must use https://. The manifest's cleartext-HTTP allowance exists for LAN development only; do not ship an app pointed at an IP address.

Endpoint registry shape
ApiClient → api_endpoints.dart → repositories → providers

Customer API surface

Unprefixed endpoint families cover auth, theme, home/storefront, products, stores/follow, search, cart, coupons, vouchers, loyalty, wishlist, checkout/hosted checkout, orders/invoices, downloads, notifications, addresses, settings, localization, content, and chat.

Media + headers

Relative media URLs resolve against the active base URL. Locale headers accompany requests; the client expects JSON and uses the secure token as a Bearer credential.

07 / SESSION

Environment, token migration, and auth boundaries

Secure storage reads api_base_url when present, but the app has no setter or settings UI for it. Fresh installs therefore use the compiled placeholder default. Secure token storage uses api_token; a legacy auth_token value is migrated once from SharedPreferences. There is no refresh-token implementation.

ConcernCurrent source behaviorBoundary
LoginEmail/password, register, Google when enabled.Backend config gates Google sign-in.
Password recoveryForgot-password OTP, send, verify and reset.No refresh-token path.
401Clears session and user-scoped state.Attempted named login push is not backed by registered routes.
LogoutUnregisters FCM and clears local state.Does not call /auth/logout.

Do not overstate session security: there is no refresh-token implementation in source, and manual logout is local cleanup plus FCM unregister—not a demonstrated server logout call.

09 / PLATFORM SERVICES

Android-only FCM startup, chat-only Ably

Unlike a lazy-after-login design, customer main() initializes Firebase before runApp. Runtime push initialization is Android-only: !kIsWeb && defaultTargetPlatform == TargetPlatform.android.

Android / FCM — startup sequence

  • Firebase project mono-customer (example ID — replace with your own project, see the walkthrough below), package com.mono.customer.app.
  • Channel high_importance_channel: “Messages and Updates”.
  • Requests alert, badge, sound, and notification permission.
  • Registers token only with an authenticated API token; stable key notification_device_id.
  • Unregisters on manual logout.

Ably / chat only — conversation transport

  • Requests GET /chat/token?conversationId=....
  • Uses private conversation.customer channel.
  • Publishes chat.message.sent.
  • No hard-coded key in source.
  • Supports customer-to-store text, image, file, presence, deduplication, and delivered state.

Never reproduce Firebase API keys, OAuth client IDs, or certificate values from the config file in docs, screenshots, or support replies.

Set up your own Firebase project, step by step

The package ships with a working google-services.json so the app runs immediately, but it points at a shared Firebase project. Create your own before you publish — it takes about ten minutes and needs only a free Google account.

  1. Create the project

    Open console.firebase.google.com and click Add project. Name it something like mono-customer and disable Google Analytics unless you want it. The project finishes creating once you confirm the analytics choice.

  2. Add the Android app

    On the project overview click the Android icon. The package name must match your applicationId character for character, so enter com.mono.customer.app until you rename it. Add a nickname and download google-services.json.

  3. Place the config file

    Copy it to android/app/google-services.json, replacing the bundled one. Both the filename and the folder are required — a wrong path still builds but throws DefaultFirebaseApp is not initialized at runtime.

  4. Enable Cloud Messaging

    In the left sidebar open Build → Cloud Messaging. The Send test message button confirms delivery works. No other FCM setup is needed.

  5. Leave the channel to the app

    The app creates high_importance_channel (“Messages and Updates”) at runtime. Do not create a matching channel in the console; the app owns it and a duplicate is ignored.

  6. Rebuild, do not hot reload

    Changing the config file needs a full rebuild. Stop the app and run flutter run -d <device> again, adding flutter clean first if the old configuration looks cached.

Finding your values. Project settings → Your apps shows the registered package name and API key. Never commit a service-account key or a private key file. The API key in google-services.json identifies the project but is not a secret on its own — access is governed by Firebase security rules.

11 / MAKE IT YOURS

Rebrand the app without writing Dart code

You can rename the app, replace its icon, and refresh the splash screen for your own store by editing configuration files and swapping two images — no Dart logic involved. The single exception is the splash tagline, which is two plain text strings in one file. Everything below works on Android and iOS.

01Swap the images

Replace assets/icons/app_icon.png and assets/icons/app_icon_foreground.png with your own 1024×1024 PNGs. Keep the same file names.

02Run one command

dart run flutter_launcher_icons regenerates every Android and iOS icon size from the flutter_launcher_icons: block already configured in pubspec.yaml.

03Rename the app

Two one-line config edits: the Android manifest label and the iOS display name. No code, no rebuild scripts.

Change the app name (Android)

Open android/app/src/main/AndroidManifest.xml and change the label on the application tag. The shipped value is Mono; the home-screen name uses whatever you put here:

android/app/src/main/AndroidManifest.xml
<application
    android:label="Your Store Name"
    ...>

Change the app name (iOS)

Open ios/Runner/Info.plist and set CFBundleDisplayName (the name shown under the icon). Leave CFBundleName as a short internal identifier:

ios/Runner/Info.plist
<key>CFBundleDisplayName</key>
<string>Your Store Name</string>

Replace the launcher icon

The icon pipeline is pre-configured. pubspec.yaml points image_path at assets/icons/app_icon.png, uses assets/icons/app_icon_foreground.png for the Android adaptive foreground, and sets #000000 as the adaptive background. Drop in your files and run:

Terminal / mono_app
dart run flutter_launcher_icons

Icon tips. Use a 1024×1024 PNG. The adaptive foreground is the mark itself with transparent padding around it (roughly the center 66%), because Android masks it into circles, squircles, and rounded squares. If your brand color is not black, also update adaptive_icon_background in the flutter_launcher_icons: block of pubspec.yaml.

Refresh the splash screen

Two layers make up the launch experience:

  • System launch screen (no code)

    Android 12 and newer build the launch screen from the adaptive launcher icon on the adaptive_icon_background color — so regenerating icons with the command above rebrands the launch screen automatically. iOS shows a plain launch image from ios/Runner/Assets.xcassets/LaunchImage; replace those images or keep the default white flash.

  • In-app branded splash (two strings)

    The animated splash then shows the brand copy: MONO. and Powered by Mono. Both are plain text strings in lib/screens/splash_screen.dart — search for 'MONO' and 'Powered by Mono' and replace the text. No layout or logic changes needed; longer brand names simply wrap.

Before you publish: the application ID (com.mono.customer.app) is a separate identity from the display name — stores require it to belong to your account. Renaming it is a five-row change documented in the next section, and it must match the Android package you register in Firebase.

Rebrand checklist — verify after each step
1. Replace assets/icons/app_icon.png + app_icon_foreground.png
2. dart run flutter_launcher_icons
3. AndroidManifest.xml  -> android:label
4. Info.plist           -> CFBundleDisplayName
5. (optional) splash strings in lib/screens/splash_screen.dart
6. flutter clean && flutter run -d <device>   # icons need a clean build

Android release signing: the release build uses debug signing. There is no key.properties, JKS, or production signing config in the package, so you must add your own before uploading to Google Play. The generic steps are: run keytool -genkey -v -keystore ~/upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload, create android/key.properties next to build.gradle.kts with your store passwords, point the release build type at that file, then rebuild. Keep the keystore and key.properties out of version control and back them up — losing the key means you can never update the listing again.

Change the application ID before you publish

Both platforms ship with the identifier com.mono.customer.app, a real reverse-domain identifier that builds fine. Google Play and the App Store each require the identifier to belong to the account publishing the app, so replace it with your own before your first upload — for example com.yourcompany.mono.customer.

Android SDK levels are pinned deliberately

The explicit number keeps uploads accepted as you upgrade Flutter. minSdk stays at maxOf(flutter.minSdkVersion, 23) because Firebase Messaging and flutter_local_notifications need a modern minimum.

14 / DEVELOPER PATH

Extend the app without breaking its architecture

01Model the payload

Add or update a typed model under lib/models/. Keep parsing close to the data shape and preserve source-backed field names.

02Add endpoint access

Register the customer path in lib/services/api_endpoints.dart and use ApiClient from a repository rather than a screen.

03Own state in a provider

Add loading, error, refresh, and mutation behavior in the matching provider under lib/providers/.

04Compose a screen

05Cover the boundary

Add or update tests under test/, then verify the affected mobile state, empty, loading, and error paths.

Screen → Provider → Repository → ApiClient → customer endpoint
                         ↘ models / services / widgets

Worked example: add a reviews feature module

Here is the five-step shape above applied to one concrete feature, so you can copy it rather than infer it. The example adds a product-reviews view backed by GET /products/{id}/reviews.

  1. Model — lib/models/product_review.dart

    A data class with fromJson that tolerates a missing optional field such as reviewer_name, so one sparse API response cannot break the whole list.

  2. Endpoint — lib/services/api_endpoints.dart

    Add a static path builder alongside the existing product routes. Keep URLs out of screens and repositories.

  3. Repository — lib/repositories/review_repository.dart

    Takes an ApiClient, fetches the list, maps each item into the model, and returns typed data or throws. No widget imports.

  4. Provider — lib/providers/review_provider.dart

    A ChangeNotifier with reviews, isLoading, and error, exposing load(productId). Register it in the MultiProvider list in lib/main.dart only if it should survive tab changes; otherwise create it in the owning screen.

  5. Screen — lib/screens/product/product_reviews_screen.dart

    A *Screen class that watches the provider and renders loading, empty, error, and populated states, reusing existing cards from lib/widgets/. Reach it from the existing product screen with Navigator.push — do not add a sixth bottom tab for it.

lib/
├─ models/product_review.dart               ← new
├─ services/api_endpoints.dart              ← add reviews path
├─ repositories/review_repository.dart      ← new
├─ providers/review_provider.dart           ← new
├─ screens/product/product_reviews_screen.dart  ← new
└─ widgets/review_tile.dart                 ← new, if reused

Test the boundary, not the pixels. A repository test asserting that fromJson survives a missing optional field, and a provider test asserting that load() sets error on failure, cover what actually breaks. Add a widget test when a screen has a non-trivial empty or error state.

Troubleshooting and FAQ

Concrete fixes for the errors that come up most during installation and first runs. Each answer names the file or setting responsible — search this page for your error text first; if the exact error is not here, the section linked in the answer holds the deeper explanation.

Install & build

“Version solving failed” when running flutter pub get

The lockfile pins Dart ^3.12.2 and a Flutter floor of >=3.44.0. Upgrade your Flutter SDK (flutter upgrade) to a release that satisfies the lock — do not downgrade the app's dependencies. The project is verified with Flutter 3.47.4.

Gradle errors about a missing wrapper on a clean clone

Gradle wrapper artifacts are deliberately not tracked. Run flutter build apk --debug once with a local Gradle 9.1.0 (Android Studio can generate it), or run gradle wrapper inside android/. The build needs JDK 17, AGP 9.0.1, and the Android SDK with compileSdk = 37 installed.

“Namespace” or manifest error after changing the application ID

Renaming the package also means moving the Kotlin source: android/app/src/main/kotlin/com/mono/customer/app/MainActivity.kt must live under folders matching your new ID, with its package line updated to match. The full four-platform rename table is in the Build & Run section.

Default FirebaseApp is not initialized at startup

The google-services.json file is missing or in the wrong folder. It must be exactly android/app/google-services.json, replacing the bundled demo project file. A config change needs a full rebuild — stop the app and run flutter run again (add flutter clean first if the old config looks cached).

Google Play rejects the release bundle / it is signed with a debug key

The shipped release build type uses debug signing. Generate an upload keystore, create android/key.properties, and point the release build type at it — the complete step list is in the Build & Run section. Keep the keystore out of version control and back it up.

Networking & API

The app launches but the storefront is empty or shows connection errors

The compiled API default points at a placeholder domain, not your server. Open lib/services/api_client.dart, change defaultBaseUrl to your own API root (for example https://your-domain.com/api/v1), and rebuild. For release builds use HTTPS; the manifest currently allows cleartext HTTP for LAN development only.

Products load but images are broken

Media URLs are relative and resolve against the active base URL, so a wrong base URL breaks images even when JSON loads. If the base URL is correct, check the backend side: php artisan storage:link must have been run and storage/app/public must be reachable under /storage on your domain.

Users are logged out immediately or see repeated 401s

The app keeps one bearer token with no refresh flow. A 401 means the backend session expired or the API URL is pointed at a different environment than the one that issued the token. Log in again; if it repeats instantly, verify the API behind your base URL is the environment you think it is.

The Google sign-in button never appears

It is conditional on backend configuration. Enable Google sign-in for the shop in the admin panel settings; the app hides the button when the backend reports it unavailable. Nothing to change in the app.

Runtime & platform

Push notifications never arrive on iOS

Runtime push initialization is Android-only by design (!kIsWeb && platform == android). iOS push requires the full Apple setup — team, APNs .p8 key, GoogleService-Info.plist, and background modes — documented in the iOS setup section. Nothing on iOS works until that checklist is done.

Push works on one Android device but not another

Tokens register only for signed-in users, and Android 13+ requires the notification permission prompt to be accepted. Check that the device granted notifications for the app and that the account completed login; the app creates its own high_importance_channel, so no console-side channel setup is needed.

A web build crashes or imports fail

Web, Linux, macOS, and Windows folders exist in the repository but are not supported targets — seven source files import dart:io. Build for Android and iOS; do not ship a web build from this package.

Some Arabic strings show in English

Built-in Arabic translations merge with server bundles, and sparse keys fall back to English by design. Missing strings come from the server's translation bundle — add them server-side rather than editing app code.

Still stuck? Reproduce with flutter run -d <device> --verbose and note the first exception, then compare against the Release readiness table — most reported issues are one of the classified limitations, not new defects.
