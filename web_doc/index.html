01 / Overview

One codebase, three front doors

MONO Marketplace is a multi-vendor commerce platform. A single Laravel application serves three completely separate front doors, and they all share one database, one permission system, and one theme engine.

STOREFRONT

Customer website

  • Themeable catalog with nine shipped storefront themes.
  • Cart, coupons, vouchers, wishlist, loyalty, and wallet.
  • Fourteen payment methods including cash on delivery and bank transfer.
  • Digital goods, bundles, and vendor chat with realtime delivery.

What ships in the package

Storefront themes

Nine themes on disk: mono (built in), plus beauty, electronics, fashion, fullwidth, grocery, home, petshop, and sports. Each is a self-contained package with its own views, assets, palette, and optional database tables.

Mobile applications

Two Flutter clients ship alongside: the customer app and the vendor app. Both talk to the same versioned API described in this document.

Web installer

public/install.php is a self-contained wizard that creates the database, writes the environment file, creates the first administrator, and activates a theme. No Composer, Node, or shell access is required on the host.

The three front doors, at a glance

Each interface is purpose-built for desktop web workflows — responsive Blade templates styled with Tailwind CSS, with zero client-side compilation steps.

Who this documentation is for

This guide covers the web product: the storefront, the vendor panel, the admin panel, and the backend services that support them. The two Flutter applications have their own companion documents. Everything here is written against the shipped source, so route names, table names, and permission keys match what you will find in the package.

There is no Vite pipeline.

Assets are plain Blade, plain CSS compiled by the Tailwind CLI, and plain JavaScript served from public/js. If you add a JavaScript entry point, add the file to public/js and reference it directly; do not look for vite.config.js or an npm run dev asset server.

The three panels

Storefront

  • Public routes in routes/web.php.
  • Views resolve through ThemeServiceProvider, which prepends the active theme's view path so theme templates win over the default ones.
  • A theme that does not supply a view falls back to resources/views automatically.
  • Uploaded media resolves through PublicMedia::url().

Vendor panel

  • Routes under prefix('dashboard') with auth:vendor, vendor.verified, and vendor.approved.
  • Layout is layouts/dashboard.blade.php.
  • Signed app-bridge routes let the Flutter vendor app open specific panel pages.

Admin panel

  • Routes under prefix('admin') with auth:admin.
  • Layout is layouts/admin.blade.php and owns the entire sidebar navigation map.
  • Every page is additionally guarded by a permission: middleware key.

Request lifecycle

The API stack prepends ForceJsonResponse and SetApiLocale; the web stack appends SetLocale. Successful API responses use a { success, data, meta } envelope. Errors are rendered by App\Support\ApiException into { success: false, error: { message, code, fields } }, so the mobile clients only ever parse one shape.

Guest redirects are area aware: an unauthenticated admin/* request lands on admin.login, a vendor or dashboard request lands on vendor.login, and everything else lands on the customer login route.

Before you start

You need the release archive mono-marketplace-installer.zip (built on your machine with python tools/build_release.py — it already contains vendor/, the compiled CSS, and the public tree, so the host needs no Composer, Node, or shell access), a cPanel or similar hosting account with MySQL, and PHP 8.3 or newer. Every screenshot below is clickable for a full-size view.

Part 1 — Create the database in cPanel

  1. Open the database manager.

    In cPanel, scroll to the Databases section and open Manage My Databases.

  2. Create the database.

    Under Create New Database, type a name after your account prefix and click Create Database. cPanel prepends the account prefix — mono becomes something like clotcode_mono. Note the full name; the installer will ask for it exactly.

  3. Create the database user.

    Scroll to Database Users → Add New User, pick a username, and generate a strong password. Note the username and password too, then click Create User.

  4. Attach the user to the database.

    In Add User To Database, select the user and the database you just created, and click Add.

  5. Grant all privileges.

    cPanel opens the privilege screen for that user/database pair. Tick ALL PRIVILEGES, then click Make Changes to save. The installer migrates and seeds through this user, so it needs full rights on this database.

Part 2 — Upload and extract the installer

  1. Open File Manager.

    In cPanel, open Files → File Manager and enter the document root of the domain you are installing on — public_html for the primary domain, or the subfolder the domain points at.

  2. Upload the archive.

    Click Upload and select mono-marketplace-installer.zip. Stay on the page until the progress bar reaches 100%.

  3. Extract it in place.

    Back in File Manager, select the zip, click Extract, keep the destination path /public_html, and click Extract Files. The archive expands into the application tree; delete the zip afterwards to reclaim the space.

Part 3 — Run the installer wizard

Visit https://your-domain.com/install.php. If .env is still missing, public/index.php also redirects the storefront's first request there automatically. The wizard is five steps and takes about a minute.

  1. Welcome — server requirements.

    The installer checks PHP 8.3+, every required extension, the presence of vendor/, and that storage/, bootstrap/cache/, and .env are writable. When each row reads Ready, continue to the database step.

  2. Database connection.

    Keep the type on MySQL / MariaDB, leave the host on localhost and the port on 3306 unless your host says otherwise, and enter the database name, username, and password from Part 1. Test connection & create tables verifies the login, writes .env, and runs the migrations. SQLite is also accepted for small or staging installs.

  3. Site & admin account.

    The site URL is auto-detected — change it only if the store will be served from another address or a subfolder. Set the store name and tagline, then create the first administrator; the account is attached to the super_admin role automatically. Leave Install the current catalog demo ticked if you want starter products, categories, brands, vendors, and bundles to explore.

  4. Pick a theme.

    Choose one of the nine storefront themes. The installer runs that theme's migrations and copies its assets. You can switch or add themes later in the admin panel under Appearance → Themes.

  5. Finish.

    The installer writes storage/app/installed.lock and shows your admin login and URLs. Log in to the Admin Panel → signs you in with a one-time token that deletes itself on first use.

Two essential post-install actions

1. Delete public/install.php immediately from the server via cPanel File Manager. Until you do, anyone navigating to the URL could re-trigger configuration.
2. Register the Laravel scheduler in cPanel Cron Jobs so order status workflows, coupon expirations, payout calculations, and SMS queues execute on time.

In cPanel, open Advanced → Cron Jobs. Set the schedule to Once Per Minute (* * * * *), and enter the command line matching your hosting account user path:

04 / Overview

Updates, scheduled jobs, and the queue worker

Applying an update

  1. Back up first.

    Copy the database and the storage/ directory. Uploads and the environment file both live outside version control.

  2. Replace the code.

    Upload the new release archive and extract it over the existing files. Do not delete storage/, .env, or public/storage during extraction.

  3. Migrate.

    Run php artisan migrate. Theme migrations are registered automatically by ThemeServiceProvider, so migrate picks up tables declared by the active theme.

  4. Rebuild CSS if you customised it.

    Run npm run build:css only if you edited resources/css/app.css or a theme stylesheet.

  5. Clear caches.

    php artisan config:clear, php artisan cache:clear, and php artisan view:clear are enough after a migration run.

There is no in-app updater.

MONO is updated by replacing files and migrating. It deliberately does not phone home or self-modify, which is what makes it safe to run on a locked-down shared host.

Scheduled jobs

Background work is data-driven rather than hard-coded in routes/console.php. The scheduled_jobs table holds each job's key, Artisan command, frequency, and enabled flag, and ScheduledJobService registers them with Laravel's scheduler at boot. Admins edit the table at /admin/settings/scheduled-jobs and can run any job on demand.

FrequencySeeded jobs
Every minuteorders:cancel-expired, ai-credits:cancel-expired
Every five minutesfeatured:expire
Dailyvendor-packages:notify-expiry, loyalty:expire-points, badges:expire-new

For these to run, the host's cron must hit /<path>/artisan schedule:run every minute. On shared hosting that is usually a cron entry in the control panel rather than a real crontab.

EVERY MINUTE* * * * * cd /path/to/mono && php artisan schedule:run >> /dev/null 2>&1

Queue worker

Three jobs send mail or push notifications: newsletter campaigns, customer push, and vendor push. A long newsletter campaign sets timeout = 1800 precisely because it chunks through subscribers in a single worker run. If you leave notifications and newsletters enabled, run a worker.

QUEUEphp artisan queue:work --tries=2
WINDOWSqueue-worker.bat

Without a worker the jobs simply sit in the jobs table. Orders, payments, and the admin panel all continue to work; only asynchronous email and push are delayed.

05 / Storefront

Themes and the theme engine

A theme is a folder under themes/ that contains a theme.json manifest. The filesystem is the source of truth: a theme exists because its folder exists, and removing the folder removes it from the admin panel.

Every theme below was activated live and captured from its home page at a desktop viewport, so what you see is what each theme actually ships — hero, palette, typography, and storefront sections.

Switching themes is instant and reversible — the admin panel activates a theme by writing one setting; no rebuild, no downtime. Captures above were taken by activating each theme in turn on the same demo catalog.

That file still lists the original eight and omits fullwidth. ThemeManager is the real source of truth; trust the themes/ directory, not the config file.

How view resolution works

ThemeServiceProvider registers resources/views/core under the core:: namespace and calls prependLocation() with the active theme's views path. That single call is what makes theming work: a theme view shadows the default view of the same name, and anything the theme does not provide falls through to the core views. The provider also registers the active theme's migrations/ path with the migrator.

Theme manifests

Each theme.json declares the slug, name, description, version, owned tables[], a full palette, and an assets block (CSS path, Google Fonts URL, body class). The palette carries per-colour labels, defaults, and CSS variable names, shape radii, an isDark flag, status colours for the seven order statuses, and logo and invoice accents.

Uninstalling deletes data.

Removing a theme drops every table declared in its manifest. Take a database backup first. This is why mono is deliberately kept outside themes/: it cannot be uninstalled out from under the site.

App themes are a separate axis

AppThemeRegistry controls the mobile app's visual system, not the website. It offers standard, marketplace, aurora, and nova, with fresh-market as the default. The registry keeps an integer version stamp in active_app_theme_version that devices diff against so the apps know when to re-fetch. Colours always come from the active storefront palette, so the app and the site stay visually consistent.

Variations

Variable products carry product_variations rows. Buyers pick attributes on the storefront and the variation modal resolves the matching row: it opens from any product card, lists one group per attribute, disables unavailable combinations, and enables Add to bag only when the chosen combination is in stock.

Shared taxonomy

Categories, brands, and attributes are shared platform-wide but can also be vendor-owned. Each carries vendor_id and an is_global flag: vendors create their own, and an administrator can promote an entry to global with the "make global" action. Categories are a tree via parent_id and can require approval before they appear.

Attributes carry values in attribute_values. The seeded demo set includes Size, Color, Storage, and Capacity.

Bundles

ProductBundleService validates and replaces a bundle's ordered item list. Variable children can be pinned to a specific variation rather than left open, and cancellation restocks every bundle line through OrderInventoryService.

Digital products are first class.

A digital product owns digital_assets, optional digital_license_keys, and per-purchase digital_entitlements. DigitalDeliveryService owns the lifecycle: an entitlement starts pending on order, becomes active on delivery, and is revoked on cancellation or refund. Download limits and expiry windows are enforced server-side.

07 / Storefront

Cart, coupons, tax, shipping, and order placement

Cart

Carts live in carts and cart_items and are shared between the website and the mobile apps. ShippingMeter produces the product-aware free-shipping progress data the cart drawer renders, and OrderInventoryService is the only place stock is decremented or restored.

Discounts

TableRole
couponsDiscount rules: type, value, minimum spend, maximum discount, usage limit and count, expiry, free-shipping flag, and scope.
coupon_customerPer-customer redemption limits.
customer_vouchersVouchers issued to customers, including loyalty tier redemptions.
loyalty_redemption_tiersTier definitions: name, points cost, voucher value, minimum spend.

VoucherService decides which coupons are publishable as vouchers and serialises the voucher cards the apps display.

Tax and shipping

TaxService is a country-and-state aware tax engine with tax classes, rates, and priorities, so it behaves the way a WooCommerce store does. Shipping is configured per method with a flat rate, a free-shipping threshold, and a free-shipping zone. Both are managed from /admin/settings/shipping and /admin/settings/taxes.

Order placement

OrderPlacementService is the single canonical path for placing an order, used by both the website and the API. It revalidates, server-side, everything the client submitted: order ownership, gateway availability, stock, coupon validity, shipping cost, and tax. Totals are always recomputed on the server; the client total is never trusted.

Never trust a client total.

That is the entire point of this service. If you add a checkout entry point, route it through OrderPlacementService rather than writing totals by hand.

Orders carry a human-readable code such as MN-98412, a denormalised customer name and email for display, and snapshot shipping details so historical invoices stay accurate after a customer edits their address book.

The internal key is card for historical reasons. normalize() maps stripe to card, and configKey() maps card back to stripe for settings storage. Use card in code and stripe in the settings table.

Configuration and availability

Credentials are stored in the settings table under gw_<gateway>_… keys and read through Setting::gateway(). They are deliberately not in .env, so an operator can rotate a key from the admin panel without touching the server. A gateway is only offered at checkout when it is enabled and every required credential is filled, as decided by PaymentGatewayService::isConfigured().

Admins configure all of this at /admin/settings/payment-gateways.

Where the code lives

Order payments

CheckoutController holds a pay* and an initiate* pair per gateway, plus paymentSuccess, paymentCancel, paymentFail, and the paymentIpn webhook receiver.

Everything else

OnlineGatewayPaymentService handles non-order payables: vendor package subscriptions, featured product promotions, and wallet top-ups. It exposes one launch() and one verify() for all twelve gateways.

Raw cURL, no SDKs.

Gateway calls are hand-rolled cURL requests in OnlineGatewayPaymentService. There is no vendor SDK in composer.json, which keeps the install light but means signature verification is your responsibility when you add a gateway.

Scope limits worth knowing

  • Vendor-facing payments are restricted to VENDOR_ONLINE_METHODS: Stripe, SSLCommerz, and PayPal only.
  • Wallet top-ups accept all twelve online gateways, but never wallet or bank_transfer.
  • Only three gateways support refunds: Stripe, PayPal, and SSLCommerz. refundStripe, refundPaypal, and refundSslCommerz live in the admin controller.

09 / Storefront

Customer accounts, loyalty, wallet, and digital downloads

Accounts

Customers register with email and password or sign in with Google. The Google client id is served from the API so the apps and the site share one configuration. Password recovery is an OTP flow: request, verify, then reset. Addresses live in a per-customer address book.

Loyalty

LoyaltyService earns points on delivered and paid orders, lets customers redeem tiers as vouchers, and expires stale balances. Every movement is a row in loyalty_transactions with its type, points, linked order or coupon, description, and expiry, so a balance is always auditable.

Administrators configure earning rules at /admin/loyalty and can adjust any customer's balance by hand with a recorded reason.

Wallet

ConcernImplementation
Balancewallets, one per customer.
Ledgerwallet_transactions with type, amount, status, reference, method, description, the acting admin, and free-form metadata.
Top-upsPending by default; an administrator approves or rejects before the balance moves.
Manual adjustmentAdministrators credit or debit any wallet from /admin/wallets.

The use it or lose it rule is deliberate: a pending top-up that is never approved is reversed rather than left dangling.

Digital library

Purchased digital goods appear in the customer's library as digital_entitlements with a download count, a download limit, and an expiry. File delivery uses a signed URL with a thirty-minute expiry, and each download is written to digital_download_logs.

Signed URLs are not access control.

A signed URL proves the link was minted by this server; it does not prove who is asking. Entitlement access is checked when the link is minted, and the file route must verify the caller before streaming. See the launch checklist before going live.

10 / Storefront

Pages, blog, menus, media, and the page builder

Pages

Built-in pages (home, about, contact, FAQ, privacy, terms) are edited at /admin/pages/<slug>/edit. Additional pages are created with the visual custom page builder at /admin/pages/custom, so non-technical staff can compose landing pages without touching Blade.

The homepage hero is a separate editor at /admin/hero. HomePageContent and HomePageSchema make it theme-aware: each theme declares which content keys exist and what fields they accept, so switching themes does not strand a half-configured homepage.

Menus

MenuService reads and writes the header and footer navigation trees at /admin/pages/menus. Menus are nestable, and the reset action restores the theme's shipped default rather than leaving an empty menu.

Blog

Posts are managed at /admin/blog with draft and publish state, cover imagery, categories, and bulk actions. Post content goes through the same translation pipeline as products and pages.

Media library

MediaService backs a shared library at /admin/media, with upload, delete, and bulk delete. Uploads are written under storage/app/public and served through PublicMedia::url().

Upload roots are enumerated by BackfillMedia and cover products, categories, brands, blog, branding, customers, vendors, admins, and AI output. The library is isolated per owner where it matters: a vendor sees their own media, an administrator sees everything.

Validate uploads server-side.

Do not trust the client extension or MIME type. Store uploads outside the document root or with a fixed safe extension, and never let an upload land on a path the web server will execute.

Cookie consent

The consent banner is configured at /admin/settings/cookie and rendered by the shared layout partial, so it appears on every theme without per-theme work.

11 / Storefront

Languages, RTL, and the translation editor

MONO ships English, Arabic, and Bengali. Arabic is a full right-to-left experience, not a mirrored stylesheet: layouts, the admin and vendor panels, and the storefront all flip, and PanelRtlLocalizationTest guards that behaviour.

Two independent defaults

This is the detail that trips people up. Each language has a web default and a separate mobile default, stored as default and default_mobile. Setting English as the web default does not make English the app default. Admins toggle each independently at /admin/languages.

Wallet approval flow

  1. Customer requests a top-up.

    The request is written to wallet_transactions as pending. Money has not moved and the balance has not changed.

  2. It appears in the admin queue.

    /admin/wallets/pending lists every outstanding request with its method, reference, and amount.

  3. An administrator approves or rejects.

    Approval credits the wallet and records the administrator. Rejection leaves the balance untouched. Neither is silent: both are ledger rows.

Unapproved requests that expire are reversed rather than left open, which is why a pending top-up never becomes a surprise balance later.

Wallet writes are auditable by design.

Every transaction row carries the acting admin_id when a person caused it, plus a reference, method, and free-form metadata. If you add a balance path, populate all four.

26 / Backend

API version 1: shape, auth, and limits

Both Flutter clients talk to the same versioned JSON API. The prefix is set once in bootstrap/app.php as api/v1; there is no content negotiation, so the version is explicit in every path.

BASE URLhttps://your-domain.com/api/v1

Response envelope

Success

{ "success": true, "data": …, "meta": { … } }. Pagination and other collection metadata live in meta, never inside data.

Error

{ "success": false, "error": { "message": …, "code": …, "fields": { … } } }. fields is present only on validation failures. Rendered centrally by App\Support\ApiException.

Authentication

Sanctum personal access tokens, sent as Authorization: Bearer. Two middleware variants exist, and the difference matters when you add a public endpoint that still wants to know who is asking:

  • auth:sanctum requires a valid token and rejects without one.
  • auth.optional resolves the user when a token is present and never rejects. The public catalog runs on it so that wishlisted and collected flags can be resolved for a signed-in customer without turning browsing into a login wall.

Rate limits

There is no global limiter. Limits are declared per route:

RouteLimit
POST /contact/send10 / min
POST /products/{id}/reviews10 / min
POST /checkout/sessions, wallet-pay, cod-pay30 / min
Vendor AI generate, generate-image, translate30 / min
Vendor messages/start10 / min
Vendor messages/{id}/reply30 / min
Auth endpoints are not throttled in this build.

Login, register, and the OTP endpoints have no rate limit attached. If you are hardening a public deployment, add a limiter to those before launch; see the launch checklist.

Signed routes

Two download routes sit deliberately outside auth:sanctum and are guarded by signed URLs with expiry instead: chat attachments at one hour, and digital product files at thirty minutes. Signing replaces the bearer token in the query string so the URL can be handed to a browser or a download manager without leaking a session credential.

Resources do the shaping.

Controllers return API Resources, not raw models: ProductCardResource, ProductDetailResource, OrderResource, WalletResource, and so on. Add a field to a Resource rather than to the model, or you will change the admin panel's own payloads by accident.

Design decisions worth knowing

Orders denormalise their customer

customer_name and email are copied onto the order, so a historical invoice still prints correctly after the customer renames their account or changes their address book.

Subscriptions snapshot their terms

Price, duration, and commission are copied onto the subscription row at purchase time, so editing a package never rewrites what a vendor was actually sold.

Settings are key and value

Runtime configuration lives in one settings table rather than in files, which is what makes the admin panel able to change mail servers and payment keys without server access.

Demo seeders

DatabaseSeeder orchestrates the rest: RolePermissionSeeder creates the three roles and the 32 permissions, LocationSeeder fills countries, states, and cities, TaxSeeder sets tax classes, and PageSeeder creates the built-in pages. Beyond that, RealisticOrderAndReviewSeeder generates plausible orders and reviews, MonoDeskKitSeeder builds a full platform-vendor bundle catalogue, and DemoDigitalProductsSeeder and ScopedVoucherSeeder populate digital goods and vouchers per audience.

Never ship the demo credentials.

The seeders create admin@mono.test and jordan@example.com, both with the password password, and eight vendors on the same password. They also embed Firebase web keys. Run migrate without --seed on a real deployment, or remove these accounts before the site is public.

Services, jobs, events, and commands

Business rules live in services, not in controllers. If a rule is about orders, money, delivery, or entitlement, it belongs in app/Services.

The services that matter most

MONEY

Billing

REALTIME

Messaging

Infrastructure

Jobs and events

Three queued jobs: SendNewsletterCampaign (chunked, timeout = 1800), SendPushNotification, and SendVendorPushNotification (both tries = 2, both pruning dead device tokens). One observer, AiCreditPurchaseObserver, fires the vendor notification when a credit purchase becomes active from any flow and de-duplicates it.

Four broadcast events run through Ably: MessageSent, MessageRemoved, ChatReceiptUpdated, and VendorNotificationReceived.

Going live: deployment and the pre-launch checklist

Production configuration

ENVIRONMENTAPP_ENV=production
DEBUGAPP_DEBUG=false
URLAPP_URL=https://your-domain.com
CRON* * * * * cd /path && php artisan schedule:run
QUEUEphp artisan queue:work --tries=2
SCHEMA CHECKphp artisan release:verify-schema
Serve everything over HTTPS.

Payment gateways reject non-HTTPS callbacks, Sanctum tokens must not travel in cleartext, and signed URLs are meaningless over an interceptable connection. Terminate TLS in front of the application and redirect HTTP permanently.

Pre-launch checklist

  1. Remove the demo data.

    Delete the seeded admin, customer, and vendor accounts, or run migrate without --seed. Confirm no @mono.test account can still authenticate.

  2. Delete the installer.

    Remove public/install.php and confirm storage/app/installed.lock exists.

  3. Set the app key and rotate the seeded Firebase keys.

    Run key:generate for a fresh APP_KEY, and replace the Firebase web configuration that the seeders wrote.

  4. Configure only the gateways you need.

    Fill in real credentials at /admin/settings/payment-gateways and leave the rest disabled. A half-configured gateway is hidden from checkout automatically, which is the behaviour you want while you set it up.

  5. Verify mail actually sends.

    Use the test-send button at /admin/settings/smtp. Until mail works, order confirmations, invoices, OTPs, and password resets all fail silently from the customer's point of view.

  6. Confirm the cron and the queue worker are running.

    Unpaid orders will not be cancelled, featured placements will not expire, and newsletters and push will not be delivered without them.

  7. Add rate limiting to the auth endpoints.

    Login, register, and the OTP routes have no limiter in this build. Add one before exposing the site publicly.

  8. Review file upload handling.

    Confirm uploads land outside any executable path, that extensions and MIME types are validated server-side, and that chat attachments and digital downloads verify the requesting user before streaming a file.

  9. Set a real admin password policy and rotate shared logins.

    Particularly before granting vendors.impersonate to anyone.

Backups

Back up the database and storage/ together. The database holds every setting, every uploaded media record, and the entire wallet and settlement ledger; storage/ holds the actual files and the generated invoice PDFs. A backup of one without the other is not a backup.

Verify a restore before you need one.

An untested backup is a hypothesis. Restore into a scratch database and run release:verify-schema to confirm the result is usable.
