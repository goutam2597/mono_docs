The gateway in one paragraph

sms_gateway is a single-purpose Flutter application, declared in pubspec.yaml as “Self-hosted SMS gateway: sends queued messages from the device's own SIM.” It runs on one Android phone that a store administrator owns. The app signs in with admin-panel credentials, exchanges them for a narrow device token, and from then on performs exactly three jobs: report its health to the backend, claim queued SMS messages and send them over the SIM, and forward inbound SMS back to the backend. Every business decision — recipient, body, timing, retry limits — belongs to the backend; the device only dials.

How it fits the marketplace

The marketplace backend owns two SMS providers: a hosted Twilio provider and this self-hosted gateway provider. When the gateway is the active provider, every outgoing message — order and OTP notifications, admin test sends — is written to the sms_messages queue instead of an HTTP call to a third party. This app is the worker that drains that queue.

Pairing

An administrator signs in with panel credentials. The backend verifies the sms.gateway.manage permission, then the app exchanges the admin token for a long-lived device token. Nothing on the phone is user-configurable.

Sending

FCM data pushes are only a wake signal. The device claims a batch, sends each message through Android's SMS manager, and reports sent or failed per message. A 5-minute claim timeout returns silent claims to the queue.

Reliability

Layered recovery: manifest-registered receivers, a data-sync foreground service, WorkManager queue passes, a 15-minute fallback poll, and a scheduled backend recovery command. Missed pushes never lose messages.

Complete Installation & Deployment Guide

Follow this step-by-step operational guide to prepare an Android phone, compile the Flutter application with your backend endpoint, configure critical battery exemptions, and register the device as the active cellular SMS gateway for the MONO Marketplace.

  1. Physical Phone Preparation & Cellular SIM Verification

    Insert your active SIM card into the Android phone. Before running any software, verify that the device is operating properly on the mobile network:

    • Disable Airplane mode and check that cellular signal bars are active with your carrier name displayed.
    • Open the phone's native Messages app and manually send a standard SMS to another number to confirm outbound delivery and active SMS balance.
    • Dual-SIM Devices: If the phone has two SIM slots, go to Settings → Network & Internet → SIMs and set your desired sending SIM as the Default SIM for SMS. Android's SmsManager will dispatch messages over this primary subscription.

  2. Enable Developer Options & USB Debugging

    To install and debug the application from your development workstation, enable developer access on the phone:

    • Open Android Settings → About Phone.
    • Locate Build Number and tap it repeatedly 7 times until you see the prompt: "You are now a developer!"
    • Go back to Settings → System → Developer Options (or Additional Settings on Xiaomi/Oppo).
    • Enable USB Debugging. On Xiaomi (MIUI/HyperOS) devices, also enable Install via USB and USB debugging (Security settings).
    • Connect the phone to your computer with a USB cable. On the phone screen, check "Always allow from this computer" and tap Allow.
    • Verify device detection in your workstation terminal:
    Terminal / ADB check
    adb devices
# Output should list your device attached:
# List of devices attached
# 84B01248000183    device

  3. Disable Android Battery Optimization (Doze Mode Whitelist)

    CRITICAL REQUIREMENT: Android aggressive power management will freeze background workers and kill foreground services if battery optimization is active. You must exempt MonoSMS from battery restrictions so it can continuously monitor incoming SMS and wake up for queue passes.

    Xiaomi / Redmi / POCO (MIUI & HyperOS)

    1. Open Settings → Apps → Manage Apps → MonoSMS.
    2. Tap Autostart → Toggle ON.
    3. Tap Battery Saver → Select No restrictions.
    4. Open Recent Apps → Long press MonoSMS card → Tap the Lock icon.

    Samsung Galaxy (One UI)

    1. Open Settings → Apps → MonoSMS → Battery.
    2. Change selection from Optimized to Unrestricted.
    3. Go to Settings → Battery & device care → Battery → Background usage limits → Add MonoSMS to Never sleeping apps.

    Oppo / Realme / OnePlus (ColorOS / OxygenOS)

    1. Open App Info → Battery Usage.
    2. Enable Allow background activity and Allow auto-launch.
    3. Pin the app in the recent tasks overview.

    In-App Shortcut

    The MonoSMS dashboard provides a direct deep link into the system battery optimization screen via the Battery settings menu item in the top overflow menu.

  4. Clone Repository & Configure Backend Endpoint

    Clone or navigate to the sms_gateway project directory and install dependencies:

    Workspace setup
    cd /path/to/mono/sms_gateway
flutter pub get

    Specify the target marketplace API endpoint using the compiled constant GATEWAY_API_URL:

    • Via Build Flag: Pass --dart-define=GATEWAY_API_URL=https://your-domain.com/api/v1 at runtime or compilation.
    • Via Source File: Alternatively, edit lib/core/gateway_config.dart directly to change the fallback default URL:
    lib/core/gateway_config.dart
    class GatewayApiConfig {
  static const String baseUrl = String.fromEnvironment(
    'GATEWAY_API_URL',
    defaultValue: 'https://your-domain.com/api/v1', // <-- Set your backend URL here
  );
}

    Local Network / LAN Testing: When deploying or testing against your backend server (e.g. https://example.com/api/v1), the Android Manifest already includes android:usesCleartextTraffic="true", allowing unencrypted HTTP connections over Wi-Fi without SSL handshakes.

  5. Set Up Firebase Cloud Messaging (FCM) Wake Channel (Optional but Recommended)

    FCM provides instantaneous wake signals to the phone whenever the marketplace puts a new SMS into the queue. The payload carries only a wake trigger (type: sms_queue_available); the message content and recipient are pulled securely from the database queue.

    1. Go to Firebase Console and open or create your project.
    2. Add an Android App with package name com.mono.sms_gateway.
    3. Download google-services.json and place it inside sms_gateway/android/app/google-services.json.
    4. In your marketplace backend admin settings (Admin → Settings → SMS Settings), ensure your Firebase Server Key / Credentials are configured.

    Works Without Firebase: If you do not configure Firebase, MonoSMS automatically runs its built-in 15-minute fallback poll and the server-side scheduled recovery worker (sms-gateway:recover), so SMS processing continues without push notifications.

  6. Build and Install the Application

    Deploy MonoSMS directly onto the connected Android device:

    Development debug run
    # Run directly on the attached phone
flutter run --dart-define=GATEWAY_API_URL=https://your-domain.com/api/v1

    To compile a standalone Release APK for production deployment:

    Release APK build
    # Build standalone release APK
flutter build apk --release --dart-define=GATEWAY_API_URL=https://your-domain.com/api/v1

# Install the built APK onto the phone via ADB
adb install -r build/app/outputs/flutter-apk/app-release.apk

    You can also copy the resulting app-release.apk to phone storage via USB cable or download it from your server browser, then tap to install.

  7. Grant Android Telephony & Notification Permissions

    When the app opens for the first time, Android will prompt for necessary telephony and service permissions:

    Permission DialogSettingOperational Purpose
    Send and view SMS messages?AllowEnables SmsManager to transmit outgoing queue messages over the cellular SIM.
    Make and manage phone calls?AllowEnables READ_PHONE_STATE to monitor carrier name, SIM status, and signal strength.
    Send notifications? (Android 13+)AllowKeeps the ongoing foreground service notification visible in the status bar.

    If any permission was accidentally dismissed, open Settings → Apps → MonoSMS → Permissions and ensure both SMS and Phone are set to Allowed.

  8. Admin Sign-In & Device Pairing Handshake

    Upon launch, the application's Auth Gate detects that no device token is stored and displays the Sign In screen:

    • Enter your marketplace Admin Email and Password (the user must have the sms.gateway.manage permission).
    • The hardware identity (Manufacturer and Model, e.g. Samsung Galaxy S22) is automatically derived from the device.
    • Tap Sign In & Register Device.

    What Happens Behind the Scenes:

    Pairing authentication sequence
    1. Phone → POST /admin/auth/login (email, password, deviceName, deviceId)
2. Backend validates admin credentials & sms.gateway.manage permission
3. Phone → POST /admin/auth/register-device (bearer admin token)
4. Backend creates SmsGatewayDevice record and issues a scoped deviceToken
5. Phone stores deviceToken in encrypted hardware storage (FlutterSecureStorage)
6. Phone discards admin password and session from active memory
7. Dashboard status immediately updates to ONLINE with green pulse indicator

  9. Verify in Admin Panel & Send a Live Test SMS

    Confirm that the phone is actively connected and test delivery through your carrier SIM:

    1. In your web browser, navigate to the Marketplace Admin Panel → Admin → SMS Gateway.
    2. Verify that your phone appears in the devices list with its correct device name, carrier, battery percentage, and a live green Connected indicator.
    3. Ensure the device status toggle is set to Active.
    4. Navigate to Admin → Settings → SMS Settings.
    5. Under SMS Provider, select Self-Hosted Gateway and save.
    6. Locate the Send Test SMS card, enter your personal mobile phone number, type a message (e.g. "Hello from Mono SMS Gateway!"), and click Send Test SMS.
    7. Within seconds, watch the phone: the ongoing foreground service will receive the wake signal, claim the message, send it through the SIM card, and report sent back to the server.

  'GATEWAY_API_URL',

TaskCommand / source
Point a build at another environmentflutter build apk --dart-define=GATEWAY_API_URL=https://store.example.com/api/v1

A gateway phone is configured only by signing in. The address is compiled in rather than typed, so an operator cannot be tricked into pointing the device at a hostile server — whoever built the APK chose the endpoint.

Pairing: from admin credentials to a device token

Paring is the only privileged moment in the device's life. It uses the administrator's account once, then immediately narrows down to a device-scoped credential.

StepCallWhat happens

Device identity is automatic

DeviceIdentity derives both values from the hardware: on Android the id is <androidId>-<model> and the name is a de-duplicated <manufacturer> <model> (so stock devices read “Pixel 8”, not “Google Pixel 8”). On iOS it uses identifierForVendor. If identity is unavailable the app still works, reporting unknown-device / “SMS Gateway”.

Signing out

signOutCleanup() cancels both timers, disposes FCM listeners, stops the foreground service, deletes the device token (secure storage) and native credentials, and returns the app to notConfigured. The backend-side device row survives so the admin can revoke or re-issue its token from the panel.

The device API surface

After pairing, every call carries the device token as a bearer token, enforced by the backend's AuthenticateSmsGateway middleware — an admin token or customer token is rejected on these routes. Responses use the platform envelope { success, data, error }; GatewayResult.fromBody parses exactly that shape.

Client behavior details

  • Token handling: the token is read from secure storage once at startup; init() never re-reads over a freshly signed-in token.
  • Error surfacing: Dio errors are translated into human messages — 401 becomes “The device token was rejected. Sign in again.”, a missing connection becomes “Could not reach the server.”
  • Log redaction: the request interceptor logs method and path, and passes bodies through AppLogger.redact, which masks sensitive keys with *** — a queued message can carry a one-time code.
  • Failure isolation: every call returns a GatewayResult rather than throwing; UI state never depends on exceptions.

The send pipeline: queue is the source of truth

FCM pushes are wake signals only — their data never contains an SMS body or recipient. Delivery is pulled, always, from the queue:

Queue guarantees

  • Single claimer: the claim transaction locks rows and stamps claimed_at, so two gateway devices can never send the same message.
  • No silent loss: a claim that never reports back is returned to pending after 5 minutes (CLAIM_TIMEOUT_MINUTES) and re-offered.
  • Bounded retries: each row carries attempts and max_attempts; a message that exhausts them is parked as failed with “Retry limit reached.” instead of looping forever.
  • Honest accounting: the send result comes from Android's SmsResultReceiver, not from the absence of an exception; failures report the carrier's reason string.

Timers while the app is alive

Once paired, the provider runs a 5-minute heartbeat (which also re-uploads the FCM token after rotation) and the 15-minute fallback poll. Both are cancelled on sign-out. The foreground service takes over durability when the app is backgrounded or swiped away.

Inbound SMS: capture, forward, deduplicate

Inbound messages (customer replies, carrier notices) flow the opposite way — from Android into the backend's sms_inbound_messages table.

Two capture paths, one truth. The broadcast receiver is primary; the inbox scan exists only because some OEMs freeze apps and swallow broadcasts. Both feed the same deduplicating endpoint.

Battery optimization

Android may freeze the gateway on aggressive OEM skins. The dashboard reads the exemption state and offers a one-tap deep link into the battery settings screen (openBatterySettings). Exempting the app is expected procedure on Xiaomi, Oppo, Vivo, and Samsung.

Setting up your own Firebase project

  1. Create a Firebase project and add an Android app with package com.mono.sms_gateway.
  2. Download google-services.json into android/app/.
  3. Enable Cloud Messaging (no APNs key needed unless you also ship iOS).
  4. Build and pair — the first heartbeat uploads the FCM token, and the admin panel shows the device as Connected.

Scheduled hygiene on the server

The sms-gateway:recover command runs on the managed scheduler. Each pass reclaims claims older than five minutes, parks retry-exhausted messages as failed, and wakes the active device for up to twenty still-pending messages. Combined with the device's own timers, no message depends on a single lucky push.

Extending the gateway safely

The architecture has one rule that keeps it safe to extend: the backend decides, the device dials. New features should preserve that split.

Add a device API call

Add the method to GatewayApiClient returning a GatewayResult, and the endpoint to the backend's sms-gateway route group behind gateway.auth. Interceptors already handle the token, logging, and error mapping.

Add a platform capability

Expose it on the single com.mono.sms_gateway/device channel: a method in GatewayNative.kt, a thin wrapper in DeviceBridge, and nothing else. The Kotlin side must stay free of queue logic.

Change the wake strategy

Replace fallbackPoll or heartbeat intervals in GatewayProvider — they are constants by design. Any new trigger should still be a pull from the queue, never a push of content.

Troubleshooting and FAQ

Concrete fixes for the errors that come up most during installation and first runs. The gateway is a real Android device doing real carrier work, so most issues are device-side — permissions, battery restrictions, or pairing — rather than code.

Install & build

“Version solving failed” when running flutter pub get

The lockfile pins the toolchain; upgrade your Flutter SDK (flutter upgrade) to a release that satisfies it instead of editing package constraints. Build with JDK 17 and the AGP/Gradle versions pinned in android/app/build.gradle.kts.

The app installs but immediately closes on launch

Rebuild after any change to google-services.json — a stale build crashes on Firebase init. The file must be exactly android/app/google-services.json, and config changes require a full rebuild (stop the app, run flutter run again, add flutter clean first if needed).

Pairing & connection

Pairing fails or the device never shows “Online”

Three things must line up: (1) the admin panel URL and credentials entered during pairing are correct and reachable from the phone's network; (2) the vendor/gateway account is active in the admin panel; (3) the phone has working mobile data or Wi-Fi. The pairing status and a Retry button with the last-sync clock appear on the device card — use it after fixing any of the three.

The device goes offline after a while (especially Xiaomi, Oppo, Vivo, Samsung)

Aggressive battery optimization is killing background work. Exempt the app from battery restrictions — the app exposes a shortcut into the battery-optimization screen, or find it under Settings → Battery → App launch / Battery optimization and set it to Unrestricted / Allow background activity. Keep the device plugged in for production duty; the device card shows the live battery level so you can monitor it remotely.

Android kills the app overnight

Same root cause as above, plus: disable “Remove permissions if app is unused” for the app, allow autostart on Chinese OEM skins, and keep WorkManager intact — the queue passes are scheduled through WorkManager, and force-stopping the app from recents can cancel scheduled work until the next FCM wake or manual open.

Sending & receiving

Messages stay queued and never send

Check, in order: (1) the device card shows Online; (2) the app holds SMS send permission — open the app once after install and grant both SMS permissions when prompted; (3) the SIM can actually send an SMS from the native messaging app (carriers block SIMs with zero usage, premium-rate restrictions, or expired plans); (4) the queue has capacity — the send pipeline processes the admin panel's pending queue in passes, and each pass retries with backoff.

Inbound replies are not forwarded to the admin panel

Inbound forwarding needs the receive/SMS permission granted and the device awake enough to observe incoming messages — the battery-optimization exemption fixes this too. Verify the inbound-sync toggle for the device is enabled in the admin panel's gateway controls, then send a test SMS to the device from another phone.

No FCM wake-up; messages send only when the app is opened

The Firebase wake channel is what pushes the device between queue passes. Confirm google-services.json matches the Firebase project registered in the admin panel, the notification permission is granted, and the device is not in Doze with no battery exemption. As a fallback, the WorkManager schedule still wakes the device periodically even without FCM.

Vendor-specific SIM behavior

The gateway sends through the SIM the device selects as default for messaging. Dual-SIM phones: set the SIM you want to bill as the default SMS SIM in Android settings, and be aware carrier rate limits apply per SIM — a flood of queued orders on one SIM can trigger carrier throttling that looks like the app failing.

Still stuck? Open the device card in the admin panel and read the live state (connection dot, battery, last sync, retry) before diving into code — the state shown there maps one-to-one onto the checks above.
