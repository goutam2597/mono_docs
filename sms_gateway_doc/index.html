The gateway in one paragraph

sms_gateway is a single-purpose Flutter application, declared in pubspec.yaml as “Self-hosted SMS gateway: sends queued messages from the device's own SIM.” It runs on one Android phone that a store administrator owns. The app signs in with admin-panel credentials, exchanges them for a narrow device token, and from then on performs exactly three jobs: report its health to the backend, claim queued SMS messages and send them over the SIM, and forward inbound SMS back to the backend. Every business decision — recipient, body, timing, retry limits — belongs to the backend; the device only dials.

How it fits the marketplace

The marketplace backend owns two SMS providers: a hosted Twilio provider and this self-hosted gateway provider. When the gateway is the active provider, every outgoing message — order and OTP notifications, admin test sends — is written to the sms_messages queue instead of an HTTP call to a third party. This app is the worker that drains that queue.

Pairing

An administrator signs in with panel credentials. The backend verifies the sms.gateway.manage permission, then the app exchanges the admin token for a long-lived device token. Nothing on the phone is user-configurable.

Sending

FCM data pushes are only a wake signal. The device claims a batch, sends each message through Android's SMS manager, and reports sent or failed per message. A 5-minute claim timeout returns silent claims to the queue.

Reliability

Layered recovery: manifest-registered receivers, a data-sync foreground service, WorkManager queue passes, a 15-minute fallback poll, and a scheduled backend recovery command. Missed pushes never lose messages.

Install and launch from the repository

The app is a standard Flutter package with no code generation step and no flavors. Fetch, configure Firebase, run.

Run sequence
git clone <your-repo> sms_gateway
cd sms_gateway
flutter pub get
# drop your google-services.json into android/app/ (optional, for FCM)
flutter run --dart-define=GATEWAY_API_URL=https://your-store.com/api/v1

What happens on first launch

  1. main() initializes device identity and Firebase before runApp, because the provider installs FCM listeners and uploads the token immediately.
  2. The auth gate finds no stored device token and shows the login screen.
  3. The administrator signs in; the app registers the device and lands on the dashboard already online.
  4. The heartbeat fires immediately, a first queue pass runs, the foreground service starts, and the 5-minute / 15-minute timers begin.

Paired phones skip login on restart. The device token lives in FlutterSecureStorage; the splash screen shows only while it is being restored, then the dashboard appears directly.

Pairing: from admin credentials to a device token

Paring is the only privileged moment in the device's life. It uses the administrator's account once, then immediately narrows down to a device-scoped credential.

StepCallWhat happens
1 · Sign inPOST /admin/auth/login with email, password, deviceName, deviceIdBackend validates the credentials and the sms.gateway.manage permission; returns a Sanctum admin token.
2 · Register devicePOST /admin/auth/register-device with name, deviceId, appVersion, bearer admin tokenBackend creates or refreshes an SmsGatewayDevice row and issues a deviceToken.
3 · Keep the narrow credential— (local)The app stores the device token in secure storage, mirrors it into the native encrypted store, and discards the admin session from active use (kept only for logout).

Device identity is automatic

DeviceIdentity derives both values from the hardware: on Android the id is <androidId>-<model> and the name is a de-duplicated <manufacturer> <model> (so stock devices read “Pixel 8”, not “Google Pixel 8”). On iOS it uses identifierForVendor. If identity is unavailable the app still works, reporting unknown-device / “SMS Gateway”.

Signing out

signOutCleanup() cancels both timers, disposes FCM listeners, stops the foreground service, deletes the device token (secure storage) and native credentials, and returns the app to notConfigured. The backend-side device row survives so the admin can revoke or re-issue its token from the panel.

The device API surface

After pairing, every call carries the device token as a bearer token, enforced by the backend's AuthenticateSmsGateway middleware — an admin token or customer token is rejected on these routes. Responses use the platform envelope { success, data, error }; GatewayResult.fromBody parses exactly that shape.

Client behavior details

  • Token handling: the token is read from secure storage once at startup; init() never re-reads over a freshly signed-in token.
  • Error surfacing: Dio errors are translated into human messages — 401 becomes “The device token was rejected. Sign in again.”, a missing connection becomes “Could not reach the server.”
  • Log redaction: the request interceptor logs method and path, and passes bodies through AppLogger.redact, which masks sensitive keys with *** — a queued message can carry a one-time code.
  • Failure isolation: every call returns a GatewayResult rather than throwing; UI state never depends on exceptions.

The send pipeline: queue is the source of truth

FCM pushes are wake signals only — their data never contains an SMS body or recipient. Delivery is pulled, always, from the queue:

Backend                    Device (MonoSMS)                Android
────────────────────────   ─────────────────────────────   ──────────────
Order placed / OTP due
  └─ sms_messages row (pending)
      └─ FCM push {type: sms_queue_available}  ──▶  wake
                                                  ├─ foreground: DeviceBridge.runNativeSync()
                                                  └─ background: GatewayMessagingService → WorkManager
POST /sms-gateway/sms/claim  ◀──────────────   authenticated queue pass
  reclaim claims older than 5 min
  lockForUpdate pending rows (≤ limit)
  mark processing, stamp claimed_at
messages[{id, to, body, kind}] ──────────────▶  for each: SmsManager send
                                                     │  SmsResultReceiver
POST /sms-gateway/sms/{id}/report ◀──────────  sent  |  failed + error
  status = sent / failed

Triggers, in order of importance

TriggerMechanismNotes
FCM pushsms_queue_available data messageForeground listener and a native messaging service that schedules WorkManager — valid even while the UI is backgrounded
ManualCheck queue now / pull-to-refreshCalls fetchAndSend() directly
Fallback pollEvery 15 minutesRecovery net for a missed or delayed push; deliberately long
Backend recoverysms-gateway:recover on the schedulerReclaims timed-out claims, parks retry-exhausted messages, nudges up to 20 pending rows with a fresh push

Queue guarantees

  • Single claimer: the claim transaction locks rows and stamps claimed_at, so two gateway devices can never send the same message.
  • No silent loss: a claim that never reports back is returned to pending after 5 minutes (CLAIM_TIMEOUT_MINUTES) and re-offered.
  • Bounded retries: each row carries attempts and max_attempts; a message that exhausts them is parked as failed with “Retry limit reached.” instead of looping forever.
  • Honest accounting: the send result comes from Android's SmsResultReceiver, not from the absence of an exception; failures report the carrier's reason string.

Timers while the app is alive

Once paired, the provider runs a 5-minute heartbeat (which also re-uploads the FCM token after rotation) and the 15-minute fallback poll. Both are cancelled on sign-out. The foreground service takes over durability when the app is backgrounded or swiped away.

Inbound SMS: capture, forward, deduplicate

Inbound messages (customer replies, carrier notices) flow the opposite way — from Android into the backend's sms_inbound_messages table.

StageComponentBehavior
CaptureSmsReceiver.ktManifest-registered for Telephony.SMS_RECEIVED at priority 999 with the BROADCAST_SMS guard — runs even when the app is closed or the phone is locked. This is the primary path.
HandoffMethodChannel eventThe receiver pushes an IncomingSms (uid, from, body, receivedAt, SIM fields) up to Dart via onIncomingSms.
ForwardPOST /sms-gateway/sms/incomingOne message per call; the uid lets the backend drop duplicates — the same message delivered twice is safe.
RecoveryInbox scanThe foreground service observes the inbox; Re-scan inbox re-offsers anything the broadcast missed while the process was frozen.

Two capture paths, one truth. The broadcast receiver is primary; the inbox scan exists only because some OEMs freeze apps and swallow broadcasts. Both feed the same deduplicating endpoint.

Battery optimization

Android may freeze the gateway on aggressive OEM skins. The dashboard reads the exemption state and offers a one-tap deep link into the battery settings screen (openBatterySettings). Exempting the app is expected procedure on Xiaomi, Oppo, Vivo, and Samsung.

Firebase is a doorbell, not a courier

Push payloads carry a single datum: type: sms_queue_available. No SMS body, no recipient, ever. If Firebase is unavailable the app still works — the fallback poll and backend recovery nudge cover the difference.

Setting up your own Firebase project

  1. Create a Firebase project and add an Android app with package com.mono.sms_gateway.
  2. Download google-services.json into android/app/.
  3. Enable Cloud Messaging (no APNs key needed unless you also ship iOS).
  4. Build and pair — the first heartbeat uploads the FCM token, and the admin panel shows the device as Connected.

Scheduled hygiene on the server

The sms-gateway:recover command runs on the managed scheduler. Each pass reclaims claims older than five minutes, parks retry-exhausted messages as failed, and wakes the active device for up to twenty still-pending messages. Combined with the device's own timers, no message depends on a single lucky push.

Narrow credentialThe app keeps a device token, not the admin session. It works only on /sms-gateway/* routes and is rejected everywhere else.

Extending the gateway safely

The architecture has one rule that keeps it safe to extend: the backend decides, the device dials. New features should preserve that split.

Add a device API call

Add the method to GatewayApiClient returning a GatewayResult, and the endpoint to the backend's sms-gateway route group behind gateway.auth. Interceptors already handle the token, logging, and error mapping.

Add a platform capability

Expose it on the single com.mono.sms_gateway/device channel: a method in GatewayNative.kt, a thin wrapper in DeviceBridge, and nothing else. The Kotlin side must stay free of queue logic.

Change the wake strategy

Replace fallbackPoll or heartbeat intervals in GatewayProvider — they are constants by design. Any new trigger should still be a pull from the queue, never a push of content.
